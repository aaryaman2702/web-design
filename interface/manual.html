Operator's manual · 2026-08-01

JARVIS

A cognitive architecture, not an assistant. 27 commits, 85 files, 7 engines, 12 commands, 23 capabilities, zero dependencies. Everything below is what exists, how it works, and the four things still waiting on you.

What you have to do

In order. The first two take about fifteen minutes together and unblock most of the system.

  1. Answer the three treatment questions ~10 min

    Which of the three scroll-film treatments you'd ship, why the other two are wrong, and what irritates you about the one you picked.

    This is the highest-value single item in the system. The taste engine has zero craft readings — every dimension that matters (typography, motion, colour, layout, pacing) is empty. Your rejections carry more information than your pick.

  2. Answer the five open questions about you ~5 min

    At the bottom of memory/self/profile.md. The profile has been rebuilt from artifacts — employment, live projects, collaborators — after its first version got the central fact wrong and had to be corrected twice.

    Four remain, and they are the ones artifacts genuinely cannot answer: is the job the direction or a base; is Break of Dawn yours, a client, or a partnership; what you think you're bad at; what you've built that you're proud of.

  3. Watch the first successful unattended run passive

    All four routines are armed and live. Capture 21:30 → dream 02:00 → brief 07:00 daily, plus evolution Sunday 10:00, all IST.

    Their first attempt failed silently — fresh sessions clone the default branch, where JARVIS doesn't exist. Fixed: every prompt now checks out the branch first and stops loudly if the system isn't there. Confirm tomorrow's brief actually arrives.

  4. Point it at work you were doing anyway ongoing

    Everything in the graph so far was produced while building JARVIS. That's the open half of the first dream's finding — the system still has no memory of your actual work.

    Next real thing you build, run /think before and /capture after. That's the whole habit.

The lesson from the first unattended run. Both the dream and the brief fired on schedule and produced nothing — and run-audit.mjs, written the day before precisely to catch that, reported "Silent: none" because of two bugs in its own logic.

Monitoring is code, and code written to check something else is never tested by the thing it monitors. A safeguard that has never fired is a hypothesis. Both are fixed and verified now, but treat any new safeguard here as unproven until you have watched it catch something real.

API keys you need

Short answer: none. Longer answer below.

Nothing is required. Every capability the system uses today runs through connectors you've already authorised with OAuth — no keys, no .env, no secrets in the repo. The scripts are zero-dependency Node; there is no npm install.

Exactly two keys are optional, and only for one thing: letting /council call other models automatically instead of you pasting.

KeyUnlocksNeeded?Reality
OPENAI_API_KEY Automated second opinions inside a council panel Optional Billed separately from ChatGPT Plus. A Plus subscription does not include API credit.
GEMINI_API_KEY Same, second panellist Optional Same trade-off. A free tier exists but is rate-limited.

Without them, /council uses the paste lane: a script compiles your question plus the relevant slice of your graph into a block you paste into ChatGPT or Gemini directly. Uses the subscriptions you already pay for, costs nothing extra, and works with any model — including ones with no API at all.

Never put keys in the repo. The memory graph is designed to travel between tools, and that's only safe if it's clean by construction. If you add keys, use environment variables — core/memory-model.md forbids storing secrets, and it's a rule with teeth: anything written to memory can end up pasted into another model.

How the system works

Five layers, ordered by how fast they change. Everything follows from that ordering.

core/Identity and cognition — the constitution, the mission, how it reasons, the graph schemachanges yearly · names no tools
engines/Seven always-on cognitive processes. Not invoked — they are the thinkingchanges rarely · names no tools
modules/Capabilities. Contract-bound, hot-swappable, installed and removed freelychanges freely · names no tools
adapters/One file mapping capabilities to actual toolsthe only layer that names a vendor
memory/The knowledge graph. Plain Markdown, typed frontmatter, typed edgesgrows forever · portable to anything

The rule that makes it survive: a module declares requires: [media.video], never a vendor name. The registry resolves that to whatever tool provides it today. Swap the vendor in 2030 and you edit one line; every module keeps working.

This isn't theoretical. Every connected service renamed itself three times during the session that built this — roughly 170 tool identifiers each time, no warning. Cost: nothing, because nothing above the adapter layer knows those names exist. A system with tool names baked into its modules wouldn't have crashed — it would have produced confident calls to tools that no longer exist, which is worse, because it surfaces as strange output instead of an error.

What it genuinely cannot do

The thinking has no ceiling. The doing is exactly as wide as that table. No banking, no phone calls, no posting to platforms you haven't connected, nothing physical. It isn't always-on — it runs when you run it, or when a routine fires. Extending it is deliberately cheap (/install + one registry line), but "everything" is an aspiration, not a spec.

Running it

git clone https://github.com/aaryaman2702/web-design.git
cd web-design
git checkout claude/personal-agentic-os-memory-3nsi26   # JARVIS lives here, not main

node scripts/doctor.mjs        # verify the architecture holds → PASS

Node 18+. No install step, no dependencies, nothing to build. Then run Claude Code from the repo root — CLAUDE.md is the boot loader and only fires if the session starts there.

The scripts

doctor.mjs — fails the build if a vendor name leaks above the adapter layer. Caught three violations in the files that define the rule, on its first run.

graph-report.mjs — contradictions, orphans, distant pairs, stale beliefs. Found four orphans on its first run.

run-audit.mjs — what failed, went silent, was never used. Caught two unused modules on its first run, and its own blind spot on its second.

council.mjs — compiles a question for another model.

context-pack.mjs — exports a graph region for anything.

dashboard.mjs — regenerates the instrument panel.

Two things worth doing

Point Obsidian at memory/. The schema uses [[wikilinks]] specifically so graph view renders your knowledge natively — live, no plugin, no build step.

Commit after capture. Memory only persists if it's committed. A /capture that writes nodes and never commits dies with the container. The routine prompts handle this; by hand it's on you.

The failure mode worth watching: a system this elaborate that goes unused is worth less than a crude one that runs daily — and the elaborateness makes that failure harder to admit. memory/graph/entities/n-jarvis-core.md records what would prove this worked and what would prove it failed, written before the outcome, so it can be graded honestly rather than rationalised later.
